# 하박조팽 로컬 AI 연결 개발 계획

상태: 계획 · 구현 시작 전 · 2026-10-17

## 목표와 순서

하박조팽 웹에서 사용자가 자신의 Codex·Claude Code를 연결해 논문 분석·질문·연구 보조에 사용한다. Windows·macOS·GUI가 있는 Ubuntu를 대상으로 한다.

사용자와 합의한 순서:

1. 기존 UI/UX에 맞춘 연결 설계를 완성하고 먼저 알린다.
2. 하박조팽에 연결 기능을 구현한다. 오케스트레이터가 여러 에이전트를 역할별로 조율한다.
3. 설치부터 권한 회수까지 통합·OS별로 검증한다.
4. 전체가 완성된 뒤 다른 웹앱용 공통 repo와 ‘대상 앱 UI/UX 맞춤부터 시작하는’ 스킬로 분리한다.

## 사용자 경험 계약

- 진입은 **AI 연결** 하나다. 설치됨·실행 중·CLI 종류를 먼저 물어보는 마법사를 만들지 않는다.
- 설치된 연결기를 종료했어도 웹 버튼이 전용 링크로 실행한다. 물리적인 설치 경로는 웹에 넣지 않는다.
- 응답이 있으면 세션·기기 권한에 따라 복구한다. 응답이 없으면 설치·다시 열기 안내로 자동 전환한다. ‘응답 없음’을 미설치로 확정하거나 설치 파일을 무한 재다운로드하지 않는다.
- 첫 설치의 파일 열기·OS 승인·필요한 최초 앱 열기는 사용자가 한다. 이후 웹의 상태 전이는 설치·앱 응답으로 이어진다.
- 처음·새 웹 세션에서는 웹의 6자리 번호를 연결기에 입력한다. 정상 갱신·재실행에 같은 절차를 반복하지 않는다.
- 모델은 처음에 무선택이다. 사용량은 20px 링과 호버·포커스·터치 상세다. 정확한 잔여 토큰 수로 표시하지 않는다.
- 웹 테마는 기존 설정을 따른다. 로컬 연결기는 다크모드다. 자동 시작·펫은 선택 사항이다.

## 에이전트 운영

오케스트레이터가 공통 인터페이스, 우선순위, 병합, 검증, 사용자 보고를 책임진다. 작업 에이전트의 완료 보고만으로 전체 완료를 선언하지 않는다.

| 역할 | 담당 | 분리할 쓰기 영역 |
|---|---|---|
| 오케스트레이터 | 계약·step 작성, 의존성 관리, 통합·회귀 확인 | 계획·공통 타입 변경 승인·통합 브랜치 |
| UI/UX 에이전트 | 기존 상단바·설정 카드·연결창·모델·링·접근성 | 전용 UI 경로·관련 UI 테스트 |
| 인증/API 에이전트 | 팀·세션·기기·연결 시도·허가·회수 | 서버 API·도메인·DB·서버 테스트 |
| CLI 실행부 에이전트 | Claude/Codex 어댑터·취소·정규화·프로세스 수명 | 연결기 core·adapter·단위 테스트 |
| 데스크톱/패키징 에이전트 | 설치·전용 링크·단일 인스턴스·업데이트·제거 | 데스크톱 UI·OS 패키징·빌드 설정 |
| 통합 QA 에이전트 | 설치·재실행·로그아웃·연결 복구 시나리오 | E2E·OS 검증 기록 |
| 독립 검토 에이전트 | 보안 경계·프로젝트 규칙·UX·누적 diff 검토 | 읽기·검토 기록, 직접 변경은 별도 배정 |

동시에 실행할 수 있는 수 안에서 파동별로 나눈다. 현재 환경에서는 오케스트레이터 + 작업 에이전트 3개까지를 기준으로 한다. 필요하면 순차적으로 다른 전문 역할을 투입한다. 같은 파일을 여러 에이전트가 동시에 수정하지 않는다.

각 작업에는 목표, 소유 경로, 입력 계약, 실패 테스트, 완료 기준, 금지 범위를 준다. 별도 브랜치·worktree로 격리하고 사용자의 기존 변경을 보존한다. 고정한 기준 commit 이후 diff로 독립 검토한다.

## 단계와 완료 기준

### 0. 연결 UX 확정

현재 단계다. 하박조팽 기존 토큰·카드·상단바·모달에 맞춰 정상·빈·진행·에러 상태를 설계한다. 클릭 시연으로 최초 설치, 종료된 앱 재실행, 설치 후 자동 전환, 6자리 오류·만료·취소를 확인한다.

완료 산출물: 위 설계서·시연, 상태 전이표, OS별 차이, 자동화 경계. 실제 연결·설치 완료라고 보고하지 않는다.

### 1. 계약·검증 기반

오케스트레이터와 서버·실행부 담당이 먼저 진행한다.

- repo 하네스에 단계별 `stepN.md`와 검증 명령을 작성한다. 장기 실행은 `scripts/execute.py <phase-dir>`로 운영한다.
- 연결 시도·ACK·기기 증명·실행 허가·취소·모델·사용량·이벤트 버전을 정한다.
- 웹 세션·활성 팀·기기·공급자의 상태를 분리한다. 늦거나 중복된 응답의 처리 규칙을 잠근다.
- CLI 작업은 선택 논문의 전달된 자료와 허용된 연구 기능으로 제한한다. 시스템 프롬프트만으로 파일·셸 권한 제한이 구현됐다고 보지 않는다.
- API·어댑터 계약의 실패 테스트를 먼저 만든다.

완료 기준: 팀·계정 간 승인 공유 금지, 취소된 시도의 ACK 거부, 임의 도메인·명령 실행 거부, 공급자별 도구 제한 방법의 실증.

### 2. 웹·서버·CLI 병렬 개발

계약 고정 후 UI, 인증/API, CLI 실행부 3개 작업을 병렬 진행한다.

- 웹은 `Topbar.actions`의 작은 인터랙티브 섬과 `/profile` 카드로 통합한다. 논문 상세에 새 탭·사이드패널을 만들지 않는다.
- 서버 읽기·쓰기는 기존 RSC / route handler / Server Action 경로를 따른다. `teamId`·소유자는 검증한 세션에서 결정한다.
- 연결기에는 Supabase service role이나 서버 비밀을 넣지 않는다. 제한된 기기 자격으로 자체 서버에 통신한다.
- 긴 AI 작업은 잡을 적재하고 durable runner와 연결한다. Vercel 요청 안에 상시 브리지 서버를 만들지 않는다.
- Claude와 Codex는 별도 어댑터다. 모델 목록·한도·오류·취소를 공통 계약으로 정규화하고, 정보가 없으면 그대로 미제공으로 전달한다.
- 조사한 agents-bridge의 현재 구현·라이선스·호환성을 재확인해 재사용 범위를 정한다. 기존 main에 Codex 완성이 있다고 가정하지 않는다.

완료 기준: 공급자별 실제 요청 1회, 스트리밍·취소·에러·미설정 처리, 모델 무선택, 데이터가 없는 사용량 처리, 사용자·팀 간 격리. 비밀 없는 build/test도 통과한다.

### 3. 데스크톱 연결기와 세 OS 패키지

Node 기반 실행부를 유지하는 최소 데스크톱 셸을 우선 검증한다. Electron/Tauri의 패키징 비용·SDK 호환성을 실제 결과로 비교해 확정한다. 연결 코드의 공통부는 특정 웹앱 UI와 분리한다.

- 설치기는 전용 링크를 OS의 실행 파일에 연결한다. 이미 실행 중이면 기존 프로세스가 요청을 받는다.
- 첫 설치는 런타임을 포함하고 별도 Node·npm 설치를 요구하지 않는다. 기존 CLI 자체의 설치·인증은 감지·안내한다.
- Windows 하위 프로세스는 창 숨김·로그·종료 코드를 보존한다. 백그라운드 동작으로 콘솔이 반복해서 나타나면 완료로 보지 않는다.
- macOS는 설치·최초 열기·앱 서명·공증·Keychain·아키텍처를 검증한다. 설치 이미지 열기와 연결기 첫 실행을 구분한다.
- Ubuntu는 지원 버전·패키지·GUI 프로토콜 등록·의존성을 검증한다. X11/Wayland의 펫 제약과 CLI 연결을 분리한다.
- 제거·업데이트·앱 이동 뒤의 프로토콜 등록과 서버 기기 권한을 정리한다.

완료 기준: 각 OS에서 실제 설치·최초 연결·종료 후 웹 버튼 재실행·업데이트·제거 기록. 패키지가 빌드됐다는 사실과 OS에서 사용 흐름이 검증됐다는 사실을 분리한다. 서명·공증이 빠진 개발 빌드를 정식 배포 파일로 안내하지 않는다.

### 4. 통합·보안·UX 검증

QA와 독립 검토 담당이 별도로 확인하고 오케스트레이터가 결과를 통합한다.

- 최초 설치 / 설치된 앱 종료 / 이미 실행 중 / PC 재부팅 / 웹 새로고침 / 브라우저 재실행.
- OS 앱 열기 허용·취소·응답 지연 / 다운로드 중복 / 설치 중 요청 만료 / 번호 불일치·만료·재발급.
- 웹 로그아웃 / 쿠키 삭제 / 새 사용자 / 팀 변경 / 공급자 로그아웃 / 연결 해제.
- 통신 단절·복구 / 늦은 ACK / 중복 콜백 / 여러 탭 / 앱 중복 실행 / 질문 중 창 닫기.
- 사용량 최신·이전·미제공·0% / 모델 목록 변경 / 사용 불가능한 모델 / 키보드·터치·좁은 화면.
- 허가 만료 이후 새 실행·결과 저장 차단, 앱의 임의 파일·셸·도메인 접근 제한.

쿠키 삭제를 서버가 즉시 알 수 있다고 약속하지 않는다. 서버 로그아웃 회수와 웹 세션 검증·짧은 실행 허가 갱신을 조합하고, 단절·세션 소실 시 차단되는 최대 시간을 검증한다. 브리지만 켜져 있다는 이유로 웹 실행 권한이 무기한 갱신되지 않게 한다.

필수 검증: 관련 실패 테스트 → 구현 → `npm run test`, 관련 Playwright, `npm run build`, `npm run lint`. 하네스 변경 시 `python -m pytest scripts/test_execute.py`. 연결기·OS 패키지에도 별도 계약·프로세스·실사용 검증을 둔다. 기존 lint 명령 자체의 호환 문제는 기능 실패와 구분해 기록·해결한다.

완료 기준: 중대한 보안·권한·주요 사용자 흐름 문제 없음, 실제 검증한 환경·버전·제약 기록, 미검증 OS를 ‘지원 완료’라고 표시하지 않음, 기존 기능 회귀 없음.

### 5. 전체 완성 후 공통 repo·스킬 분리

이 단계는 앞 단계 완료 후에 한다. 지금 repo나 스킬을 먼저 생성하지 않는다.

- 공통 연결기·프로토콜·CLI 어댑터·OS 패키징을 분리하고 하박조팽은 첫 소비 앱으로 유지한다.
- 웹앱별 표시명·색 토큰·허용 origin·서버 인증·팀 표시·다운로드 배포 정보를 설정 가능한 어댑터로 만든다.
- 서로 다른 웹앱의 승인·로그아웃·모델·사용량을 격리한다. 하나의 프로토콜 스킴을 여러 설치기가 서로 덮어쓰는 구조를 피한다.
- 두 번째 호스트 설정 fixture로 하박조팽 이름·URL·인증이 하드코딩되지 않았는지 검증한다.
- 스킬은 `skill-creator` 절차로 만들고 **대상 앱 UI/UX 조사·설계부터** 시작한다. 이후 계약 연결, CLI/설치기 구성, 세 OS 검증으로 이어지게 한다.
- 새 repo의 범위·라이선스·소비 방법·지원/미검증 환경을 기록한다. 저장소나 스킬 분리로 하박조팽이 동작하지 않게 되는 변경은 허용하지 않는다.

## 보고 원칙

각 단계에서 완성된 화면·동작, 실제 실행한 검증, 남은 제약을 보고한다. 설계 시연, 단위 테스트, Windows 실사용, macOS 실사용, Ubuntu 실사용을 서로 대체하지 않는다. 외부 인증·서명·실제 OS 환경이 필요하면 어떤 검증이 아직 남았는지 명확히 남긴다.

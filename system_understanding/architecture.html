아키텍처 & 토폴로지

프로토타입은 단일 클라이언트 SPA지만, 프로덕션은 Vercel(Next.js 15) + Supabase + 외부 durable 잡 러너가 얽힌 서버리스 시스템입니다. 아래는 그 토폴로지, 경계, 데이터 흐름입니다.

🔄
ADR-016 — ADR-010·012를 개정한 현재 스택. 이전 설계는 SQLite의 영속 디스크 요구(②)와 인-프로세스 워커 필요(①) 때문에 "상시 구동 Node 서버, 서버리스 금지"였습니다. Supabase 채택으로 ②가 사라지고, ①은 외부 durable 잡 러너로 대체되어 서버리스 배포가 성립합니다. 실시간(SSE)은 Supabase Realtime이 인-프로세스 이벤트 버스를 대체합니다.

읽기 vs 쓰기 — 데이터 흐름 (ADR-015)

CLAUDE.md의 "서버 로직은 서버에서만" 규칙을 RSC 시대에 맞게 구체화합니다.

경로방법비고
읽기 (조회)서버 컴포넌트(RSC)에서 lib/ 서버 함수로 Prisma 직접 조회클라이언트가 DB를 직접 보지 않음 → 규칙 충족. 초기 페인트 빠름
쓰기 (변이)Server Action 또는 route handler (app/api/**)zod 검증·권한·작성자 주입 여기서. 변이 후 revalidatePath/Tag
인터랙티브 섬클라이언트 컴포넌트 ("use client")live룸·관점토글·스케줄편집·업로드모달·명령팔레트만
실시간 수신Supabase Realtime 구독폴링 대신 푸시(ADR-014→016)

백그라운드 작업 (ADR-013 + ADR-016) — CRITICAL

🔥
분석·arXiv 가져오기·녹화 후처리는 요청 경로에서 인라인으로 돌리지 않습니다. Claude 분석은 분 단위라 Vercel 함수 실행 시간 제한을 넘기기 때문입니다. 업로드 성공과 분석 성공을 아키텍처로 분리하며(ADR-013), 서버리스에선 실행 주체가 인-프로세스 워커가 아니라 외부 durable 잡 러너입니다(ADR-016).

실시간 동기화 (ADR-014 → ADR-016) — Supabase Realtime

live는 모두에게 즉시 일관돼야 합니다(ADR-001). 폴링 대신 푸시한다는 ADR-014의 의도는 유지하되, 메커니즘을 인-프로세스 SSE 버스에서 Supabase Realtime으로 교체합니다(서버리스/다중 인스턴스에서도 성립).

외부 서비스 경계

🟢 Supabase Postgres

관리형 DB(ADR-016, SQLite 대체). Prisma 연결은 pooled DATABASE_URL(서버리스 커넥션 풀링) + 마이그레이션용 DIRECT_URL.

🟢 Supabase Storage + Realtime

Storage: PDF·에셋·figure를 프리사인 업로드(서버는 서명만) / 단기 서명 URL로. Realtime: live·@멘션 전이 푸시(인-프로세스 SSE 버스 대체).

⏱️ Durable 잡 러너

Inngest 확정(ISSUES I-15; Trigger.dev/QStash 검토 대상이었음). 분석·arXiv·녹화 후처리를 실행(ADR-016). 재시도·멱등·관찰성 내장. Vercel route handler가 enqueue, 러너가 Anthropic 호출.

☁️ Cloudflare Stream Live

앱은 Live Input 생성·권한 체크·플레이어 노출만(ADR-002, 변경 없음). 녹화 완료는 웹훅(HMAC)으로 Vercel route handler가 수신. 송출 자격증명은 발표자에게만.

🤖 Anthropic API

논문 분석. 잡 러너에서만 호출(분 단위). 사람이 검수·보강하는 보조 추출(ADR-011). 키는 서버 환경변수 전용.

🔗 arXiv

잡 러너가 arxiv.org/pdf/{id} PDF를 가져와 Supabase Storage에 저장(요청 경로 아님). SSRF 화이트리스트.
